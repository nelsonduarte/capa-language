# Feasibility study: a native LLVM backend for Capa

> Status: design spike / feasibility assessment (2026-06-09). This is
> NOT an implementation plan and NOT a commitment. It is a clear-eyed
> read of what a from-scratch native backend would cost, what it would
> buy over the Wasm AOT path that already exists, and a recommendation
> on whether and when to start. Grounded in the current code
> (`capa/ir/`, `capa/ir/_emit_wasm/`, `capa/runtime/`) and in the
> existing roadmap docs (`roadmap-technical-detail.md`,
> `roadmap-security-performance.md`).

---

## 0. Executive summary

A native LLVM backend is technically feasible and would reuse a large
fraction of the existing pipeline (the CIR, the monomorphiser, much of
the memory-layout design, and the parity harness shape). But the honest
assessment is that **it should be deferred**. The marginal value over
the already-shipped Wasm AOT path (`capa build --release`, which
Cranelift-compiles to native) is small for Capa's actual positioning,
while the cost is large and front-loaded by two genuinely hard
sub-arcs: a real memory manager / GC, and a second host-bridge runtime
re-implemented outside Python. The roadmap already records the
anti-scope decision ("Do NOT build an LLVM backend from scratch; Wasm
AOT covers 90% of the value at 10% of the cost"), and nothing in the
current code or benchmark data contradicts it.

The crux is not the toolchain choice or the ABI. It is the
**marginal-value-over-Wasm-AOT question**, which collapses into a
single test: is there a concrete target that Wasm AOT provably cannot
reach (a perf-bound consumer where the sandbox indirection is measured
to matter, a deployment surface with no Wasm runtime, or a native-FFI
requirement)? Today there is no such driver, and the headline of the
project ("the Wasm backend IS the sandboxing / supply-chain story")
actively argues against trading it away for raw native speed.

## 1. Motivation and fit

### 1.1 What exists today

Capa has two backends plus an AOT path:

- **Python transpiler** (`capa transpile`): the correctness ORACLE.
  Every other backend is held byte-identical to it.
- **Wasm Component Model backend** (`capa/ir/_emit_wasm/`): lowers CIR
  to WAT, parses to a `.wasm` via `wasm-tools`, runs through `wasmtime`
  (which JIT-compiles with Cranelift).
- **Wasm AOT** (`capa build --release`, `capa run-aot`,
  `capa/runtime/_aot.py`): serialises a Cranelift-compiled `.cwasm`
  via `Module.serialize()`, so each run is `Module.deserialize()` +
  host bridges, no re-compile. This is recorded as DONE in
  `roadmap-technical-detail.md` (P1).

The decisive framing fact: **the Wasm backend already produces
AOT-compiled native execution.** Cranelift is a production native code
generator. "Wasm backend" does not mean "interpreted"; it means
"native code generated by Cranelift, executing inside a thin wasmtime
sandbox with host-provided capability bridges."

### 1.2 What a native LLVM backend would add over Wasm AOT

Concretely, and only these:

- **No Wasm sandbox indirection.** No linear-memory bounds model, no
  host-call boundary for capabilities, no wasmtime instance. For
  CPU-bound code the gap is usually small (Cranelift output is close to
  LLVM -O2 for straight-line numeric code); the indirection cost is
  mostly at the capability/host-call boundary, which Capa programs hit
  relatively rarely on hot paths.
- **LLVM's optimiser.** `-O2`/`-O3`, LTO, autovectorisation. Real but
  workload-dependent. For Capa's typical shape (struct/list/string
  manipulation, not dense numerics) the realistic delta over Cranelift
  is modest.
- **Smaller / dependency-free standalone binaries.** A native binary
  with a statically linked runtime can be smaller and has no wasmtime
  dependency. (Note: the Wasm AOT launcher today still rides on the
  Python `wasmtime` package; a Rust launcher was deferred precisely
  because the gain did not yet justify it, per P1.2(b).)
- **Direct native FFI.** Calling C libraries by the C ABI without the
  Component Model / WIT marshalling layer. This is the one capability
  that Wasm genuinely makes awkward, and the most plausible future
  driver.
- **Targets with no Wasm runtime.** Embedded / bare-metal / a platform
  where shipping wasmtime is unacceptable.

### 1.3 Weighed against positioning

Capa's stated moat (`roadmap-security-performance.md`) is
**capabilities + IFC + a machine-verifiable SBOM**, with "performance
sufficient for production", not "fastest native code". The Wasm
backend is not just a code generator in this story: it is the
**sandboxing / supply-chain enforcement surface**. The host-bridge
boundary is where capability attenuation is enforced at runtime (the
handle-table fix in `wasm-cap-handles.md` lives exactly there). Trading
the Wasm sandbox for raw native speed trades away part of the security
narrative for a perf win that the benchmark data does not show anyone
needing.

The benchmark suite (`benchmarks/README.md`) measures the *Python
transpiler* against hand-Python and lands at 1.0x-1.45x overhead. It
does not even measure Wasm-AOT-vs-native, because no consumer has
posed that question. **There is currently no measured performance
driver for a native backend at all.**

Candid verdict on 1.x: the marginal gain (sandbox-free perf + native
FFI + Wasm-less targets) is real but narrow, and none of it is
currently demanded. It does not justify a multi-month backend today.

## 2. The hard design decisions

### 2.1 Lowering path: CIR -> LLVM IR, or a new lower-level IR?

The CIR (`capa/ir/_nodes.py`, produced by `capa/ir/_lower*.py`) is the
right entry point and is already backend-agnostic in spirit: it is
ANF-flavoured (every sub-expression bound to a fresh local), which maps
cleanly onto SSA. The monomorphiser (`capa/ir/_monomorphise/`) runs
before emission and is fully backend-agnostic, so an LLVM backend
consumes monomorphic CIR exactly as the Wasm backend does.

What is reusable from the Wasm lowering vs Wasm-specific:

- **Reusable (the bulk):** `_lower.py`, `_lower_expr.py`,
  `_lower_stmt.py`, `_lower_pattern.py`. These produce CIR, not WAT.
  They are about ANF, alpha-renaming, attenuation-map construction,
  pattern desugaring, struct/sum/typestate shape decisions. None of
  this is Wasm-specific.
- **Wasm-specific (not reusable):** everything under
  `capa/ir/_emit_wasm/`. The string (ptr, len) expansion, the i32
  pointer model, the canonical-ABI return-area dance (`_caps.py`), the
  WAT text emission. A native backend re-implements the emission layer.

Recommendation: lower **CIR -> LLVM IR directly**. The CIR is already
low enough (explicit allocations, explicit field offsets via the layout
module, explicit control flow). Inserting a new lower-level IR between
CIR and LLVM would be a third IR to maintain with no clear payoff;
LLVM IR is itself the low-level IR. The one caveat is that the CIR
leaves some type strings under-resolved (the `_layout.py` fallbacks
default unknown element types to `Int`); a native backend with strict
ABI needs those resolved, which may push some type precision back into
the lowerer or analyzer (a shared cost that would also benefit Wasm).

### 2.2 Toolchain: how to produce LLVM IR from Python

The compiler is Python. Options:

- **llvmlite** (Numba's LLVM binding). Pros: in-process IR builder,
  no text round-trip, JIT + object-file emission, mature, pip-installable
  wheels for the major platforms. Cons: pins a specific LLVM version,
  heavy binary dependency, the IR builder API tracks a subset of LLVM,
  Windows support is real but the wheel/toolchain story (linker, libc)
  is the rough edge. This is the most likely choice if proceeding.
- **Emit textual `.ll`, shell to `clang`/`llc`.** Pros: zero Python
  binding dependency, trivially inspectable output (good for an oracle
  workflow), decouples from llvmlite's version pin. Cons: requires an
  LLVM toolchain installed on the build host, text generation +
  re-parse is slower, and you hand-maintain `.ll` syntax (error-prone).
  Reasonable for a first slice / spike because it keeps the dependency
  surface zero and the output auditable, matching the project's
  oracle-first habit.
- **inkwell (Rust) via subprocess.** Adds a Rust component to a
  Python project. Only makes sense if a Rust launcher already exists
  (it does not; P1.2(b) was deferred). Rejected for now.
- **Cranelift-direct as the lighter alternative.** Capa *already
  depends on Cranelift transitively* (via wasmtime). A native backend
  could target Cranelift IR directly (`cranelift-codegen`), skipping
  both Wasm and LLVM. Pros: the dependency is already paid for; faster
  compile than LLVM; the team already understands Cranelift output
  characteristics from the AOT work. Cons: Cranelift has no Python
  binding (would need a Rust shim, same objection as inkwell); weaker
  optimiser than LLVM, so it gives up much of the "native is faster"
  argument that motivates the project in the first place. If the only
  goal were "native binary without wasmtime at runtime," Cranelift-
  direct is the honest lighter path; but then the delta over Wasm AOT
  shrinks to "no sandbox + no wasmtime dependency," which is thin.

Toolchain recommendation if proceeding: textual `.ll` for the spike
(zero dependency, auditable), llvmlite if it graduates to a real
backend. Do not add a Rust component unless the Rust launcher arc
(P1.2(b)) is funded independently.

### 2.3 Value representation / ABI: can `_layout.py` be reused?

`_layout.py` is the most reusable asset and also the place that needs
the most rework. The DECISIONS transfer; the CONSTANTS do not.

What transfers (the design):

- Struct = pointer to a record; fields laid out in declaration order
  with natural alignment (`compute_struct_layout`).
- Sum = tag at offset 0, payloads from offset 8 in a uniform 8-byte
  slot (`compute_sum_layout`).
- String = (ptr, len) pair.
- List/Map/Set = 16-byte header (len, cap, data_ptr, pad) + separate
  element array.
- The multi-impl-trait **type-id header** at offset 4 for shared
  dispatch (`_TYPE_ID_OFFSET`, `_TYPE_ID_HEADER_SIZE`). This dispatch
  design is backend-neutral and reusable as-is.
- Option/Result/JsonValue/IoError pre-registered layouts.

What must change (the encoding), because Wasm32 bakes in 4-byte
pointers and i32 addressing:

- **Pointer width.** Every "i32 pointer / 4-byte pointer" assumption
  (`_size_of` returns 4 for struct/sum pointers; the List/Map headers
  pack four 4-byte words into 16 bytes) becomes 8-byte pointers on a
  64-bit native target. The 16-byte header would no longer hold four
  pointer-sized fields; layouts that mix i32 cap/len with pointers
  need re-derivation. This is not a tweak of a constant; it is a
  parameterisation of the whole module by pointer width.
- **Alignment.** Natural alignment on 64-bit means 8-byte alignment
  for pointers and i64/f64. The current `_align_up` logic is sound but
  the per-type sizes feeding it change.
- **Calling convention.** Wasm uses the canonical ABI / return-area
  dance for multi-value host returns (`_caps.py`). Native uses the C
  calling convention (struct-return, registers). The string (ptr, len)
  pair would pass as two registers or a small struct; the multi-value
  return shapes get re-expressed in C-ABI terms.
- **The String packing trick.** Several places pack (ptr, len) into a
  single i64 (e.g. closures pack `(fn_idx << 32) | env_ptr`). On 64-bit
  these packings break (a pointer no longer fits in 32 bits); closures
  and packed strings need a real two-word representation.

Honest read: `_layout.py` should be **refactored into a width-and-
alignment-parameterised core** that both backends consume, rather than
copied. That refactor is itself a non-trivial, regression-prone change
to the Wasm backend (it touches `_structs.py`, `_lists.py`, `_maps.py`,
`_sets.py`, `_closures.py`, `_strings.py`), and it must keep Wasm
parity green throughout. Treat it as a prerequisite cost, not free
reuse.

### 2.4 Memory management: this is the major sub-arc

The Wasm backend uses a **bump allocator** (`_emit_alloc_function` in
`_runtime.py`): align to 8, advance `heap_top`, `memory.grow` per page,
trap at a source-declared memory cap. No free, no GC. This is fine for
short CLI runs (the process dies, the OS reclaims) and is the same
limitation the roadmap's P2 (real GC) exists to address.

A native backend faces the same question but cannot lean on "the wasm
instance is torn down and linear memory vanishes." Options:

1. **Keep bump + arena, native.** Allocate a large arena via `mmap` /
   `VirtualAlloc`, bump within it, free the whole arena at exit. This
   is the cheapest path and is honest for a first slice: it has exactly
   the same long-running-process leak the Wasm backend already has, so
   it ships no regression relative to the status quo and unblocks
   everything else. Recommended for the minimal slice.
2. **Reference counting.** A refcount word in each object header,
   `retain`/`release` emitted at copy/drop points. The linear-handle
   work (S1, DONE) already computes drop points, so the release sites
   come partly for free. Does not collect cycles, but Capa's value
   model rarely creates them (no arbitrary shared mutability). This is
   the roadmap's stated cheaper alternative to tracing GC.
3. **Tracing GC.** A real collector. This is a multi-month arc on its
   own, with all the classic hazards (stack-map generation so the
   collector can find roots in LLVM-generated frames, write barriers,
   precise vs conservative scanning). Avoid unless a long-running
   native service makes it unavoidable.

The honest assessment: **the GC question is the second crux** (after
marginal-value). A native backend that wants to host long-running
services needs at least refcounting and probably tracing GC, and that
is precisely the work the Wasm GC proposal lets the Wasm backend
sidestep (P2 option 1 reuses the host runtime's GC). This is a concrete
case where Wasm is *easier*, not harder, than native: the native path
must build a collector that Wasm can borrow from the host.

### 2.5 Capability host bridges: scope this honestly

The Wasm host (`capa/runtime/_wasm_host.py`, ~2050 lines) defines ~30
host functions across 11 capability namespaces:
`capa:host/{stdio,clock,env,fs,random,net,db,proc,json}`. These are
where capabilities cross to the OS, and where attenuation is enforced
(the handle-table design in `wasm-cap-handles.md`).

A native backend needs the equivalent: either syscall shims emitted
into the native code, or a **C/native runtime library** the generated
code links against, re-implementing all 11 namespaces AND the
attenuation enforcement that travels with each handle. There are two
sub-options:

- **Re-host in Python (FFI back to the existing host).** The native
  code calls back into the existing Python `_wasm_host` logic via
  ctypes/cffi. Keeps one source of truth for capability enforcement,
  but reintroduces a Python dependency and a boundary cost, undercutting
  the "dependency-free native binary" motivation.
- **Re-implement the runtime natively (Rust/C).** A standalone runtime
  with no Python. This is the honest native story but **duplicates the
  ~2050 lines of host bridges plus the attenuation logic**, and it is
  the same objection that deferred the Rust Wasm launcher (P1.2(b)):
  duplicating security-critical enforcement in a second language is a
  parity-and-audit liability, not just LOC.

Scope: a minimal slice can ship with `stdio` only (and maybe `clock`),
deferring the other nine namespaces. But a *useful* native backend
eventually re-implements the full surface, and every one of those
bridges is a place the Python-vs-native parity bar must hold.

### 2.6 Parity: holding LLVM to the byte-identical bar

The core project invariant is byte-identical output across backends vs
the Python oracle (`tests/test_ir_wasm_parity.py`: compile + run both
backends in-process, assert stdout matches exactly). The known carve-
outs are documented (float formatting needed a Grisu2 port to reach
parity; non-deterministic caps like Clock/Env/Fs are excluded to keep
runs deterministic).

An LLVM backend would be held to the same bar by adding a
`tests/test_ir_llvm_parity.py` of the same shape: run the same
`_PARITY_PROGRAMS` list through the native binary, capture stdout,
assert it matches the Python oracle byte-for-byte. The parity harness
is therefore reusable as a *pattern* (the program list and the assert
shape transfer); the runner needs a new arm that builds and executes
the native artifact instead of instantiating wasmtime in-process.

The hard parity risks specific to native: integer overflow/wrap
semantics (the lowerer already had to handle i64::MIN, see P3), float
formatting (must port the same Grisu2 path or share it), and any place
the 32-bit-vs-64-bit representation change leaks into observable output
(it should not, but hash/iteration order in Map/Set must be verified).

## 3. What to reuse vs build new

| Component | Reuse / build | Notes |
|---|---|---|
| CIR (`_nodes.py`) | **Reuse as-is** | Backend-agnostic; ANF maps to SSA. |
| Lowering (`_lower*.py`) | **Reuse as-is** | Produces CIR, not WAT. |
| Monomorphiser (`_monomorphise/`) | **Reuse as-is** | Already backend-agnostic. |
| Layout *design* (`_layout.py`) | **Refactor + reuse** | Parameterise by pointer width/alignment; design transfers, constants do not. |
| Type-id dispatch header | **Reuse design** | Offset-4 type-id is backend-neutral. |
| Emission (`_emit_wasm/`) | **Build new** | WAT/canonical-ABI specific. |
| Allocator | **Build new (bump on mmap first)** | Same leak as Wasm bump; GC is a later arc. |
| Host bridges (`_wasm_host.py`) | **Build new (or FFI back)** | ~2050 LOC + attenuation; the biggest build-new cost after GC. |
| Parity harness | **Reuse pattern** | New runner arm builds + runs native artifact. |
| Python oracle | **Reuse as-is** | Still the source of truth. |

## 4. Scope options and a recommended minimal first slice

### 4.1 Scope ladder

- **Spike (proof it lowers at all):** CIR -> textual `.ll` for a
  scalar-only subset (Int/Bool/Float arithmetic, `if`/`while`, function
  calls, `println` via a single hand-written `stdio` shim). No structs,
  no heap, no caps beyond stdout. Goal: confirm the lowering shape and
  produce one byte-identical "hello / fizzbuzz" against the oracle.
- **Minimal useful slice:** add structs + the bump-on-mmap allocator +
  the layout-width refactor. Still scalars + structs only; Strings as
  (ptr, len); no List/Map/Set, no closures, no GC; `stdio` + maybe
  `clock`. A `test_ir_llvm_parity.py` over the scalar/struct subset of
  `_PARITY_PROGRAMS`.
- **Real backend:** Lists/Maps/Sets/closures/traits, the full host-
  bridge surface, refcounting or GC. This is the multi-month body.

### 4.2 Recommended minimal first slice (if proceeding)

Core scalar + struct subset to native with the bump-on-mmap allocator,
no GC, `stdio` only:

- **Covers:** Int/Bool/Float, struct construction + field access,
  `if`/`while`/`for`, function calls + recursion, `println`, byte-
  identical parity against the oracle on the scalar/struct subset.
- **Does NOT cover:** Lists/Maps/Sets, closures, trait dispatch,
  pattern match on sums beyond the simplest cases, any capability
  except stdout, GC / long-running processes, native FFI (the actual
  motivation), multi-platform linking guarantees.

Note what this slice deliberately omits: it does **not** demonstrate
the native-FFI advantage (the one capability Wasm genuinely lacks),
because FFI lands late. So even the slice does not validate the
strongest motivation early, which is itself an argument for deferral.

## 5. Effort and risk

### 5.1 Effort

Honest range, assuming the existing CIR/monomorphiser are reused:

- Spike: ~1-2 weeks.
- Minimal useful slice (scalars + structs + bump alloc + layout
  refactor + stdio + parity harness): **~4-8 weeks**, dominated by the
  layout-width refactor (must keep Wasm parity green) and getting the
  native linking/toolchain reliable across platforms.
- Real backend (full containers, full host bridges, GC): **several
  more months**. The full host-bridge re-implementation and the GC arc
  are each large enough to be their own multi-slice efforts.

This is consistent with the roadmap's framing of a from-scratch LLVM
backend as "an arc of many months."

### 5.2 Top risks

1. **GC.** The single largest open-ended risk. Refcounting is
   tractable (S1 gives drop points); tracing GC with LLVM stack maps
   is a research-grade sub-project. Wasm sidesteps this via the host
   GC proposal.
2. **ABI / 32-to-64 representation change.** The layout refactor
   touches every collection/closure emitter and must not break Wasm
   parity. High regression surface.
3. **Platform / linking.** Producing a working native binary on
   Windows + Linux + macOS (linker, libc, static vs dynamic) is the
   classic "the last 20% is 80% of the pain" of any native backend.
4. **Host-bridge duplication.** ~2050 LOC of capability bridges plus
   attenuation enforcement, re-implemented natively, is a parity-and-
   audit liability (the same reason the Rust Wasm launcher was
   deferred). Capability enforcement is security-critical; a second
   implementation is a second thing to audit.
5. **Parity carve-outs.** Float formatting, integer wrap, Map/Set
   iteration order must each be re-validated against the oracle.

### 5.3 Prerequisites

- The layout module refactored to be pointer-width/alignment
  parameterised (benefits Wasm too; can be done independently first).
- Tighter CIR type resolution so the native ABI does not rely on the
  `_layout.py` "default unknown to Int" fallbacks.
- A decided memory-management strategy (bump-then-refcount is the
  honest staged answer).
- A concrete driver (see Recommendation). Do not start without one.

## 6. Recommendation

**Defer.** Do not start a native LLVM backend now. The recommendation
is the same one already recorded in `roadmap-security-performance.md`'s
anti-scope section, and the current code and benchmark data reinforce
rather than weaken it:

- Wasm AOT already delivers native code generation (Cranelift) with a
  shipped, audited host-bridge surface and the capability-enforcement
  story intact.
- The benchmark suite shows no measured demand for sandbox-free native
  speed; it does not even measure that axis, because no consumer has
  asked.
- The two hardest sub-arcs (GC, native host bridges) are precisely the
  things Wasm makes *easier* (host GC proposal; one audited host
  implementation), so going native pays for them twice.
- The project's moat is capabilities + IFC + SBOM, in which the Wasm
  sandbox is an asset, not an obstacle.

**Start only when a concrete driver appears.** Any one of these would
justify revisiting:

1. **A measured perf-bound consumer** where profiling shows the wasm
   sandbox / host-call boundary (not the algorithm) is the bottleneck,
   and Cranelift-via-wasmtime is demonstrably the floor. (Measure
   first; the AOT work already provides the benchmark harness.)
2. **A hard native-FFI requirement** a real consumer needs and the
   Component Model / WIT path cannot serve ergonomically. This is the
   most plausible trigger.
3. **A deployment target with no acceptable Wasm runtime** (embedded /
   bare-metal / a platform where shipping wasmtime is disallowed).

If a driver appears, start with the spike then the minimal slice in
section 4.2, and do the layout-width refactor as an independent,
parity-preserving prerequisite first so the risk is taken in isolation.

### The crux, restated

The decision does not hinge on toolchain (llvmlite vs `.ll` vs
Cranelift-direct) or on the ABI mechanics, both of which are solvable
engineering. It hinges on the **marginal-value-over-Wasm-AOT
question**: there is no current target that Wasm AOT cannot reach, and
the two things native would add (sandbox-free perf, native FFI) are
either undemanded or not yet load-bearing. The GC sub-arc is the second
crux, and it is the clearest illustration of the first: native makes
Capa *pay* for memory management that Wasm lets it *borrow*.
