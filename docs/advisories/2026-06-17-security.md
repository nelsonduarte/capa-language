# Capa security advisory, 2026-06-17: capability-attenuation, information-flow, encapsulation, manifest, and supply-chain fixes

> **Status.** Published with the `1.4.0` release. All findings below
> were remediated in the hardening window between `v1.3.0` (2026-06-16)
> and `v1.4.0` (2026-06-17). Most fixes tighten the static analysis,
> the runtime capability enforcement, or the manifest builder so a
> program (or a manifest) that previously compiled or over-claimed is
> now rejected or claims less; every such change is claimed here under
> the [`STABILITY.md`](../../STABILITY.md) **security exception** (the
> same soundness-fix carve-out Rust and Python follow), and is
> therefore shipped as a **MINOR** bump, not a MAJOR one. The rationale
> is stated per finding below.

This advisory satisfies the `STABILITY.md` requirement that a security
fix changing observable behaviour without a major bump "ships with a
security advisory ... [that] states explicitly what changed and why the
change is not subject to the major-bump rule."

Affected versions: `1.3.0` and earlier on the `1.x` line.
Fixed in: `1.4.0`.
Reporter / process: internal hardening pass for the `1.4.0` release.
Channel: this advisory; cross-referenced from
[`SECURITY.md`](../../SECURITY.md) and the `1.4.0` `CHANGELOG.md` entry.

## Why these are security fixes, not breaking changes

Every finding below is a case where the compiler, the runtime
capability enforcement, or the manifest builder **accepted**,
**enforced too weakly**, or **affirmed** something that violates a
first-class, machine-checked Capa security property: capability
attenuation and enforcement, information-flow control over `@secret`
data (including the `@constant_time` discipline), capability
encapsulation, the manifest's `provably_excluded_capabilities` claim,
or the supply-chain trust root the package manager rests on. All of
these are in scope per [`SECURITY.md`](../../SECURITY.md) (the
capability-discipline guarantees, "Compilation accepts a program where
a `@secret` value reaches a public sink that the analyzer should
reject", and the integrity of the published manifest / supply-chain
artefacts). The prior behaviour was a soundness or enforcement bug, so
tightening it falls squarely under the `STABILITY.md` security
exception and does not force a major bump. The direction of every
change is reject-more, enforce-more, or claim-less, and only programs
that were already unsound, runtime calls that already escaped their
restriction, or manifests that already over-claimed are affected.

## New rejections (read before upgrading)

Three of these fixes turn a program that **previously compiled** into a
compile error. They are listed up front because they are the most
likely to be noticed on upgrade; each is a soundness fix under the
security exception, and the legitimate shape of each pattern keeps
compiling (see the per-finding precision notes):

- **`@constant_time` secret compare (finding B2).** A `@constant_time`
  function that compares a `@secret` `String` or `List` with a
  short-circuiting operator (`==`, `!=`, `<`, `<=`, `>`, `>=`) or with
  `starts_with` / `ends_with` / `contains` / `index_of` is now
  rejected as a timing oracle.
- **`Unsafe` hidden in a capability-bearing struct (finding C2).**
  `Unsafe` is now rejected as a struct field even inside a
  capability-bearing struct, and the Wasm backend refuses an
  `Unsafe`-bearing parameter type recursively.
- **Field access through an abstract-capability or trait receiver
  (finding C1).** Reading a field off a value whose static type is an
  abstract capability or trait is now rejected.

## A. Capability attenuation and enforcement (3 findings)

A capability carries an authority that an attenuator (`restrict_to`,
`allows`) is supposed to narrow, and the runtime is supposed to enforce
that narrowing on every privileged operation. The following three gaps
let the attenuation be evaded or the enforcement be bypassed.

### A1. `Proc.restrict_to` fixed only the basename, not the binary identity

**What changed.** `Proc.restrict_to("git")` was meant to confine a
process capability to the `git` binary, but the check matched only the
command's **basename**, so a planted absolute path with the same
basename (`/attacker/git`) passed. A bare-name restriction now admits
only bare-name commands (basename equality, or the leading-`-` plugin
suffix form) and rejects any command carrying a path separator; a
restriction that is itself a path gates on the resolved, normalised
path. Python and the Wasm host enforcement (`$proc_allows`) stay in
sync; the guest-side `.allows` query is a lexical approximation of the
same rule via a new `$str_has_slash` helper, with the authoritative
realpath enforcement on the host side.

**Security impact.** A sandbox-defeating RCE vector: a restriction
intended to pin the binary to a trusted `git` could be satisfied by an
attacker-controlled binary of the same basename planted on a path the
program would run.

**Exception rationale.** The restriction is a capability-attenuation
guarantee the runtime publishes; enforcing the binary's identity rather
than its basename restores the documented discipline. Security
exception, MINOR.

### A2. `Db.allows` did not canonicalise the path before the boundary check

**What changed.** `Db.allows` compared the requested database path
against the allowed prefix **lexically**, so a `prefix/../escaped.db`
traversal that escapes the prefix on disk passed. `Db.allows` now
canonicalises the path and the prefix through `realpath` before the
boundary check, exactly as `Fs.allows` already does, so the escaping
path is denied. The literal-collapse path on the Wasm side normalises
`..` lexically before its boundary check; both Wasm hosts enforce the
privileged ops through the receiver capability's `allows()`, so the fix
lands on both backends.

**Security impact.** A `..`-traversal that escapes the intended
database directory, opening a database outside the granted prefix.

**Exception rationale.** Same capability-attenuation class as A1;
mirroring the `Fs` canonicalisation closes the traversal. Security
exception, MINOR.

### A3. `Db` open was vulnerable to a symlink TOCTOU between check and open

**What changed.** `Db.allows` canonicalised and validated the path
(after A2), but between that check and the actual `sqlite3` open, the
path could be swapped for a symlink pointing outside the allowed
prefix (a time-of-check / time-of-use race). After opening, the runtime
now re-derives the connection's **true path** from the kernel and
re-validates it against the capability's prefix, closing the file
descriptor and refusing if it now resolves outside the prefix.

**Known residual.** `sqlite3` does not accept a pre-opened file
descriptor, so a narrow residual window remains between the kernel-side
open and the true-path re-derivation; it is documented as a residual
rather than claimed closed.

**Security impact.** A TOCTOU symlink swap could open a database
outside the granted prefix even after the path check passed.

**Exception rationale.** The capability's prefix is an enforcement
guarantee; re-validating against the kernel's true path after open
restores it for the realistic attack window. Security exception,
MINOR.

## B. Information-flow and constant-time (3 findings)

Capa's information-flow control is a first-class, machine-checked
security property: a `@secret` value must not reach a public sink
without an explicit `declassify`, and a `@constant_time` function must
not branch or short-circuit on a `@secret`. The following three gaps
dropped a `@secret` label or admitted a timing oracle.

### B1. A variable reassignment dropped the secret label in the default tier

**What changed.** An IFC variable reassignment (`x = secret`) joined the
RHS label onto the target only under `@strict_ifc`; in the default
(warn) tier the assignment silently dropped the label, so a later sink
of `x` did not warn. The reassignment now joins the RHS label onto the
target **unconditionally**, like `let x = secret`, in the default tier
too; only the pc (implicit-flow) join stays strict-gated.

**Known residual.** The join is monotonic on the target Symbol (it
never lowers the label); the resulting flow-insensitivity is a known
pre-existing limitation, not introduced here.

**Security impact.** Silent laundering of a `@secret` (PII, a token) to
a public sink in the default tier, by routing it through a reassigned
variable.

**Exception rationale.** Exactly the in-scope IFC class `SECURITY.md`
names. The accepted programs were already unsound. Security exception,
MINOR.

### B2. A `@constant_time` function admitted a secret string / list compare

**What changed.** A `@constant_time` function could compare a `@secret`
`String` or `List` with a short-circuiting comparison (`==`, `!=`, `<`,
`<=`, `>`, `>=`) or with `starts_with` / `ends_with` / `contains` /
`index_of`, all of which return early on the first differing element.
That is the classic MAC / token / password compare timing oracle
(CWE-208). Such a comparison on a `@secret` operand is now rejected.
Int / Float scalar comparison stays allowed (constant-time on the
hardware paths Capa targets); the dedicated XOR-accumulate compare in
`capa_hash` (whose parameters are not `@secret`) is unaffected.

**Security impact.** A timing side channel: the running time of the
short-circuiting compare leaks how many leading bytes of a secret
matched, recoverable byte-by-byte by an adversary who can time the
function.

**Exception rationale.** `@constant_time` is a published guarantee that
the function has no secret-dependent timing; admitting a
short-circuiting secret compare violated it. This is a **new
rejection** of a program that previously compiled; it is a soundness
fix under the security exception. MINOR.

### B3. Under `@strict_ifc`, an early return inside a secret branch leaked the predicate bit

**What changed.** Under `@strict_ifc`, a divergence (`return`, `break`,
`continue`, `panic`) inside a secret-conditioned branch lowered the pc
back at the end of the branch, so a sink on the line **after** the
branch did not see the implicit flow, even though reaching that line at
all depends on the secret predicate. The pc now stays elevated for the
rest of the enclosing block after a divergence under a `@secret` guard,
so a post-branch sink that leaks the predicate bit is flagged. The
elevation is monotonic and strict-only; it does not lower across an
`@strict_ifc` function boundary (the pc is reset to public on function
entry and restored on exit, so the elevation no longer contaminates the
next `@strict_ifc` function checked).

**Security impact.** A `@secret`-conditioned implicit flow that
survives an early return: the bit of the secret predicate could be
inferred from whether control reached a public sink, with no diagnostic
under `@strict_ifc`.

**Exception rationale.** Same in-scope IFC class as B1, reached through
an implicit flow under `@strict_ifc`. Security exception, MINOR.

## C. Capability encapsulation (2 findings)

A capability's authority and an implementor's private fields are
encapsulated: a holder of an abstract-capability or trait value may
call only its declared methods, and the built-in FFI escape hatch
`Unsafe` must never be smuggled behind an abstract capability. The
following two gaps let that encapsulation be pierced.

### C1. Field access through an abstract-capability or trait receiver

**What changed.** Reading a field off a value whose static type is an
**abstract capability or trait** (`lg: Logger` ... `lg.fs`) type-checked
and ran. The runtime value is the concrete implementor, so reaching its
private field exercised a built-in capability the signature never
declares, and the implementor's fields are private to its `impl`. Field
access through such a receiver is now rejected. Access through the
concrete struct type, and `self.field` inside the `impl`, stay allowed
(the legitimate reachable-via-struct model).

**Security impact.** An encapsulation bypass that defeats the
capability-confinement claim: a function holding only an abstract
`Logger` could reach the concrete logger's `Fs` field and exercise
authority its signature never declares, invisible to the manifest.

**Exception rationale.** The capability-discipline guarantee is that a
function's authority is bounded by its declared signature; reaching a
private field through an abstract receiver violated it. This is a
**new rejection** of a program that previously compiled; soundness fix
under the security exception. MINOR.

### C2. `Unsafe` hidden in a capability-bearing struct

**What changed.** The capability-bearing relaxation (which lets the
attenuable built-in caps live as struct fields) admitted `Unsafe` as a
field of a capability-bearing struct, so the FFI escape hatch could
hide behind an abstract capability. `Unsafe` is now rejected as a
struct field even in a capability-bearing struct; the relaxation covers
only the attenuable built-in caps (`Fs` / `Net` / `Db` / `Proc` /
`Env` / `Clock` / `Random`). The Wasm backend's `Unsafe` rejection now
also walks a parameter type recursively (struct fields, sum payloads,
generic args) so an `Unsafe`-bearing type is refused loud rather than
emitting an invalid `call $py_import`.

**Security impact.** `Unsafe` is the FFI trust boundary; smuggling it
inside a capability-bearing struct would let arbitrary host calls hide
behind an abstract capability, defeating the entire confinement model.

**Exception rationale.** Same encapsulation class as C1, on the most
dangerous capability. This is a **new rejection** of a program that
previously compiled; soundness fix under the security exception.
MINOR.

## D. Manifest / SBOM integrity (3 findings)

`provably_excluded_capabilities` is the manifest's machine-checkable
claim that a function provably **cannot** reach a given capability, and
the provenance / SBOM digest is the byte-stable identity a downstream
consumer verifies against. A false exclusion or a digest that misses a
module is a supply-chain soundness bug.

### D1. False exclusion of a user-capability exercised through a cap-bearing struct

**What changed.** `provably_excluded_capabilities` falsely excluded a
**user-defined capability reachable through a capability-bearing
struct**: a holder of `S` where `impl C for S` can exercise `C`, so a
function whose signature touches `S` can reach `C`. The reachability
walk did not propagate the user-cap through the struct, so it stayed in
the exclusion list while a method call exercised it. `C` is now placed
in `transitively_reachable_capabilities` and out of the exclusion list.
The bound is derived from the signature, so it stays sound regardless
of the body (conservative: may over-declare, never under-declare).

**Security impact.** A manifest that over-claims: a capability
advertised as provably excluded was actually reachable through a
cap-bearing struct. A downstream consumer trusting the SBOM's exclusion
claim would be misled about the function's authority.

**Exception rationale.** The manifest is a published, machine-checked
security artefact; a false exclusion is a soundness bug in the
capability-discipline guarantees it makes. Declining the false claim is
a soundness fix under the security exception. MINOR.

### D2. False exclusion via a capability nested in a struct field or a sum-variant payload

**What changed.** The same false exclusion fired when the cap-bearing
type is **nested** inside another struct's field, and again when a
capability is reachable **only** through a sum-type variant payload
(`type Wrap = Carry(SmtpMailer) | Nope`, where `match w { Carry(m) ->
m.send(...) }` exercises the cap). The reachability walk seeded only
user-caps and structs and never expanded variant payloads, so a cap
reachable only through nesting or a sum payload escaped the closure.
Every struct and every sum / union is now seeded, and the caps
reachable through each nested field and each variant payload are folded
into one fixpoint at any nesting depth, for both built-in and user
caps. A struct or sum with no cap-bearing field / payload (a plain enum,
a pure-data struct) still permits exclusion (no over-approximation).

**Security impact.** The same manifest over-claim class as D1, reached
through nesting or a sum-variant payload; an attacker-equivalent bypass
of the D1 fix had it shipped alone.

**Exception rationale.** Same in-scope manifest-soundness class as D1;
completes the closure of the false-exclusion hole. Security exception,
MINOR.

### D3. The provenance / SBOM digest did not cover every module, and single-file identifiers drifted

**What changed.** Two related digest / identifier issues. First, the
provenance and SBOM digest covered only a subset of the linked modules,
so a change in an uncovered module did not change the digest a consumer
verifies; the digest now covers **all** modules in the link, and a
cross-module mangled name (`sel__`, `_capa_m<N>__`) is demangled in the
capability names so the auditor sees the author's name. Second,
`program_source_digest` took the multi-file `<display>\n<sha256>` join
whenever the sources map was non-empty, but the CLI always forwards
`linked.sources`, which for an import-free program holds exactly one
entry, so every single-file program's `serialNumber`,
`documentNamespace`, and `invocationId` silently moved off their
historical values. The single-root case now falls back to the bare
`sha256(source)`, reproducing the pre-existing seed byte-for-byte; the
multi-file join is taken only when more than one module is linked.

**Security impact.** A digest that omits a module is a supply-chain
integrity gap: a change in an uncovered module is invisible to a
consumer verifying the attestation. The identifier drift broke
byte-reproducibility of single-file SBOMs against their historical
values.

**Exception rationale.** The provenance / SBOM digest is a published,
machine-verified supply-chain artefact; covering every module and
restoring the stable single-file identity restores its integrity.
Security exception, MINOR.

## E. Supply chain (3 findings)

The package manager's trust rests on GPG signature verification and on
refusing to vendor content from an untrusted or traversing source. The
following three gaps weakened that trust root.

### E1. GPG verification was anchored on the signing subkey, not the primary key

**What changed.** `_verify_signed_pin` and the registry index verifier
compared the configured `verify_key` / root key against the
**signing-key** field of the GnuPG `VALIDSIG` line, so verification
broke (or could be steered) when a publisher rotated to a dedicated
signing subkey. They now compare against the **primary-key**
fingerprint (the last field of `VALIDSIG` per GnuPG `doc/DETAILS`); gpg
already proves the subkey-to-primary binding, so anchoring on the
primary keeps verification working across a subkey rotation. The
mismatch diagnostic now reports both the subkey used and the primary.

**Security impact.** Anchoring on the wrong field made verification
brittle across legitimate key rotation and muddied the identity the
trust decision rests on.

**Exception rationale.** Signature verification is the supply-chain
trust root; anchoring it on the stable primary-key identity restores
the intended guarantee. Security exception, MINOR.

### E2. `file://` git URL traversal, including percent-encoding

**What changed.** A `file://` git dependency URL could carry a `..`
path component (`file://prefix/../x`, with either separator) and escape
the intended directory to vendor arbitrary local content. Any `..`
component in a `file://` URL is now rejected. A follow-up closed the
**percent-encoded** form: git percent-decodes a `file://` path before
resolving it, so `file://%2e%2e/x` (and `/a/%2e%2e/b`, mixed-separator,
uppercase) still escaped; the path is now decoded with a single
`urllib.parse.unquote` (the exact depth git resolves: `%2e%2e` becomes
`..` and is rejected, while a double-encoded `%252e` stays the literal
filename `%2e`, matching git) and separators normalised before scanning
for `..`. Plain absolute `file://` paths stay accepted.

**Security impact.** A path-traversal that vendors arbitrary local
content from outside the intended directory into the project tree.

**Exception rationale.** Refusing a traversing dependency source is a
supply-chain integrity guarantee; closing both the literal and the
percent-encoded form restores it. Security exception, MINOR.

### E3. The registry index trusted a present signature when gpg was unavailable

**What changed.** When the registry index carried a signature but `gpg`
was not on `PATH`, the verifier warned and trusted the index instead of
failing closed, even though the index is the registry's trust root. It
now **fails closed** in that case, matching the tag-verification path;
the existing `CAPA_REGISTRY_ALLOW_UNSIGNED` opt-out still rescues
air-gapped / self-hosted mirrors. The docs now also note that an
index-derived `verify_key` is TOFU anchored on the root key (weaker
than a hand-pinned key) and record the single-root-key
single-point-of-failure limitation, and that `Random` (SplitMix64) is
not cryptographically secure.

**Security impact.** Trusting a signed index without being able to
verify the signature is a fail-open trust root: a tampered index would
be accepted on any host lacking gpg.

**Exception rationale.** The index is the registry trust root; failing
closed when it cannot be verified restores the intended guarantee.
Security exception, MINOR.

## F. Input robustness (1 finding)

### F1. `parse_int` could be driven to an uncaught error by a many-digit string

**What changed.** `parse_int` called `int(body)` before checking the
magnitude, so a string with more digits than CPython's int-to-str
conversion cap tripped an uncaught `ValueError` (a denial-of-service on
the parser). `parse_int` now screens the **significant** digit count
(leading zeros stripped) and returns `None` for an out-of-range
magnitude before calling `int(body)`, so a many-digit string no longer
crashes and an in-range value with a long zero run still parses. This
matches the Wasm `$parse_int`, which accumulates digit-by-digit and
where leading zeros never overflow the i64 accumulator, so both
backends now agree.

**Security impact.** A denial-of-service: untrusted input with a long
digit run could crash the parser with an uncaught exception.

**Exception rationale.** A robust parser that returns `None` on
out-of-range input rather than crashing is the documented behaviour;
the prior crash was a bug. Security exception, MINOR.

## Precision (no over-tainting, no false rejection, no over-approximation)

For the attenuation fixes, a bare-name `Proc` command and a legitimate
in-prefix `Db` path keep working; for the IFC fixes, a declassified
value, an all-public flow, and an Int / Float compare under
`@constant_time` are clean; for the encapsulation fixes, access through
the concrete struct type, `self.field` inside the `impl`, and a
capability-bearing struct holding only attenuable caps stay valid; for
the manifest fixes, a struct or sum with no cap-bearing field / payload
still permits exclusion and a single-file SBOM reproduces its
historical identity; for the supply-chain fixes, a subkey-signed pin, a
plain absolute `file://` path, and a verifiable signed index are all
accepted. The changes reject (or decline to claim, or enforce) only the
programs that were already unsound, the runtime calls that already
escaped their restriction, or the manifests that already over-claimed.
