# csv_parser

A CSV parser of the stdlib `csv` shape (the canonical Python
module for ingesting comma-separated tabular text, shipped with
every Python install).

## What the library does

Parses a CSV text blob into rows of cells by:

1. Walking the input character by character through a two-mode
   state machine (unquoted vs. quoted field).
2. In unquoted mode, ending the cell on the delimiter character
   and ending the row on `\n`.
3. In quoted mode, treating `""` as a literal quote inside the
   cell and treating a lone `"` as the field terminator.
4. Stripping a trailing `\r` from each cell so Windows `\r\n`
   line endings collapse cleanly to `\n`, and dropping the
   empty trailing row produced by a file ending with `\n`.

The naive public API is
`parse_csv(text: str, delimiter: str = ',') -> list[list[str]]`.

## Authority surface

*(none)* - pure string transformation; sits alongside slugify/,
tabulate/, textwrap/, and humanize/ as a pure-case in the
study.

## Why representative

Three reasons:

1. **It is universally deployed.** CSV is the most-used
   structured-text format in data tooling, and the stdlib `csv`
   module ships with every Python install. Essentially every
   data-ingest script, ETL job, or notebook that reads tabular
   text reaches for a CSV reader of exactly this shape. The
   public API surface is recognisable to any Python programmer.
2. **It exercises a shape the other pure cases do not.** Where
   `slugify`, `textwrap`, and `humanize` are single-pass string
   transformations and `tabulate` walks a pre-built nested
   list, this parser is a character-by-character state machine
   whose output is itself a `List<List<String>>`. That stresses
   Capa's nested-collection handling on the output side and
   `String.substring`-based char-by-char scanning on the input
   side, neither of which the other pure pairs cover. The
   structural-parser shape is shared with `ini_loader/` and
   `dotenv/`, but those produce `Map`-shaped output from a
   line-split loop; this one produces nested lists from a
   per-character scanner.
3. **It is the PURL-silence case taken to its limit.** The
   naive Python has no imports at all, not even `typing`. A
   PURL-based SBOM for the file says literally nothing about
   the file's behaviour. The Capa version, by contrast, names
   all five helpers and declares zero capabilities per
   function, with the compiler proving each one pure - so the
   SBOM-diff gap on a pure file with non-trivial parsing logic
   is exactly the per-function attribution that PURL cannot
   carry.

## Naive Python's PURL SBOM proxy

The top-level import block is empty: `naive.py` imports
nothing. A PURL-based SBOM generated by syft / pip-licenses for
this file therefore says nothing beyond "depends on Python
itself", with no per-function attribution and no signal that
the functions are pure.

The Capa SBOM names zero capabilities for every helper and the
compiler proves it: a hidden Fs / Env / Net / Unsafe call in
any of `scan_unquoted`, `scan_quoted`, or `parse_csv` would be
rejected at type-check time because no such capability is in
scope.

Note on scope: Capa does not yet support default parameter
values at the function-signature level, so `delimiter: String`
is a required argument in the Capa version where the Python
defaults it to `","`. `main` exercises the conventional default.
The capability-attribution point this pair makes is independent
of default-argument support.
