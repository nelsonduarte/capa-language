# textwrap

A paragraph wrapper of the stdlib `textwrap` shape (the
canonical Python module for line-wrapping help text, log
messages, and other CLI output).

## What the library does

Wraps an arbitrary paragraph to a maximum line width by:

1. Splitting the input into words on any run of whitespace
   (spaces, tabs, newlines).
2. Greedily packing words into lines no wider than `width`,
   inserting a single space between consecutive words.
3. Leaving any single word that is wider than `width` on its
   own line rather than splitting mid-word (matching the
   stdlib's default `break_long_words=False` mode).

The naive public API is
`wrap(text: str, width: int = 70) -> list[str]` and its
newline-joined sibling
`fill(text: str, width: int = 70) -> str`.

## Authority surface

*(none)* - pure string transformation; sits alongside slugify/
and tabulate/ as a pure-case in the study.

## Why representative

Three reasons:

1. **It is universally deployed.** `textwrap` is a stdlib
   module, so every Python install ships it; essentially every
   CLI tool that prints help text or log messages reaches for
   `wrap` or `fill` at some point. The shape of its public API
   is recognisable to any Python programmer.
2. **It is the cleanest pure-case match in the study.** Unlike
   `slugify`, there is no Unicode-normalisation gap to paper
   over: word boundaries are whitespace, which Capa's
   `String.split` handles natively, so the Capa transliteration
   is a one-to-one behavioural mirror of the Python rather than
   a stand-in.
3. **It is the PURL-silence case taken to its limit.** The
   naive Python has no imports at all, not even `typing`. A
   PURL-based SBOM for the file says literally nothing about
   the file's behaviour. The Capa version, by contrast, names
   every helper and declares zero capabilities per function,
   with the compiler proving each one pure.

## Naive Python's PURL SBOM proxy

The top-level import block is empty: `naive.py` imports
nothing. A PURL-based SBOM generated by syft / pip-licenses for
this file therefore says nothing beyond "depends on Python
itself", with no per-function attribution and no signal that
the functions are pure.

The Capa SBOM names zero capabilities for every helper and the
compiler proves it: a hidden Fs / Env / Net / Unsafe call in
any of `split_words`, `wrap`, or `fill` would be rejected at
type-check time because no such capability is in scope.

Note on scope: Capa does not yet support default parameter
values at the function-signature level, so `width: Int` is a
required argument in the Capa version where the Python defaults
it to 70. `main` exercises a typical width of 40. The
capability-attribution point this pair makes is independent of
default-argument support.
