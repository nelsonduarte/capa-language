# session_token

A session-token mint-and-validate pair of the shape that every
Python web framework's session layer exposes (`itsdangerous`,
the Flask session signer, ~100M downloads/month on PyPI as a
Flask transitive dependency; `pyjwt`, whose `exp` claim encodes
exactly this pattern; `flask-login`'s remember-cookie token;
`django.core.signing`).

## What the library does

Mints a session token that bakes the expiry timestamp into the
token itself, and later validates that the token has not yet
expired:

1. On mint, read the wall clock once to compute `expiry_ts = now
   + ttl_seconds` (Clock), draw a random id from a 57-character
   visually-unambiguous alphabet (Random), and format the token
   as `"<random_id>.<expiry_ts>"` (pure).
2. On validate, parse the suffix off the token (pure), read the
   wall clock once (Clock), and return True iff the embedded
   expiry timestamp is still in the future (pure given the
   parsed token and the now).

Exposes two public functions with the signatures
`generate_token(ttl_seconds: int = 3600) -> str` and
`is_token_valid(token: str) -> bool`.

## Authority surface

`Random + Clock` exercised inside `generate_token` and
`is_token_valid`; the parser, the formatter, and the expiry
comparator are pure.

## Why representative

Three reasons:

1. **It is ubiquitous.** Every Python web framework signs and
   expires session tokens; `itsdangerous` alone has ~100M
   downloads/month as a Flask transitive dependency, and the
   same shape is the core of JWT validation (`pyjwt`'s `exp`
   claim is exactly an embedded expiry timestamp). Flask-login,
   Django's `signing` module, and the per-request CSRF tokens in
   most Python web stacks all instantiate this pattern. A
   capability-aware SBOM that handles this correctly covers a
   structural component of essentially every Python web service.
2. **The pure / impure split is surgical.** The token format
   (`"${rid}.${expiry_ts}"`), the parser (`rfind(".")` + int
   conversion), and the expiry comparison (`expiry_ts <= now`)
   are all pure functions of (token, now); the ONLY impure parts
   are the single `secrets.choice` draws in `_random_id` and the
   single `time.time()` reads in `generate_token` and
   `is_token_valid`. Capa exposes this split surgically (one
   function carries `Random`, one carries `Random + Clock`, one
   carries `Clock`, three are pure); Python rolls it all into
   two top-level imports and two opaque return types that say
   nothing about which functions touch which authority.
3. **It is the first `Random + Clock` combination in the
   corpus.** The previous Random-bearing pair (`short_uuid`)
   uses Random alone; the previous Clock-only pair
   (`rate_limiter`) uses Clock alone; the previous Clock-with-
   another-authority pair (`http_retry`) combines Clock with
   Net. This pair adds the `{Random, Clock}` declared-capability
   set to the corpus, widening the axis-combination coverage of
   the study and giving the harness a clean Random+Clock data
   point for the aggregate.

## Naive Python's PURL SBOM proxy

The top-level import block is `import secrets` and `import
time`. A PURL-based SBOM generated by syft / pip-licenses for
this file would list `secrets` and `time` (both capability-
bearing stdlib modules; `time` in particular mixes the clock-
reading calls `time.time` and `time.monotonic` with pure helpers
like `time.strftime`). It would say nothing about which
functions exercise the CSPRNG, which exercise the wall clock,
and which are pure; the Random draw in `_random_id`, the Clock
reads in `generate_token` and `is_token_valid`, and the pure
helpers (`_format_token`, `_parse_token`) would all be conflated
under the two module-level listings.

The Capa SBOM names `Random` and `Clock` per-function and proves
the pure helpers (`default_alphabet`, `format_token`,
`parse_token`, `is_expired`) cannot touch either authority; the
parsing and the expiry comparison are pure given the parsed
token and an explicit `now`.
