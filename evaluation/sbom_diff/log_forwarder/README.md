# log_forwarder

A tail-and-forward log shipper of the shape that every
observability sidecar exposes (Datadog Agent's file tailer,
Filebeat's harvester, the Splunk Universal Forwarder, a
homegrown Loki / Grafana / Sentry forwarder).

## What the library does

Reads the tail of a log file from disk, formats the lines as a
JSON array, and ships the payload to a collector URL:

1. Open the log file and slice off its last `max_lines` lines (Fs).
2. Format the slice as a JSON array literal (pure).
3. Send the payload to the collector (Net).

Exposes a single public function with the signature
`forward_log(path: str, url: str, max_lines: int = 100) -> int`
that returns the count of lines forwarded.

## Authority surface

`Fs + Net` exercised inside one composition function; the
formatter is pure and the signature of the naive Python version
declares neither authority.

## Why representative

Three reasons:

1. **It is ubiquitous.** Every observability sidecar in
   production does some form of this: tail a file, ship the
   contents over the wire. Datadog, Splunk, Elastic, Loki, and
   essentially every in-house Python forwarder script implement
   the same Fs-then-Net pipeline. A capability-aware SBOM that
   handles this pattern correctly covers a structural component
   of essentially every observability deployment.
2. **The shape conflates Fs and Net under one signature.** Same
   structural failure as `config_loader`'s `load_config(path)`
   and `http_retry`'s `fetch_with_retry(url, ...)`: one
   function exercises two distinct authorities, and the
   signature names neither. A reviewer reading
   `forward_log(path, url, max_lines)` cannot tell whether the
   disk read happens before or after the network send, whether
   the file path is read once or watched, or whether the URL is
   contacted on every call or buffered.
3. **It surfaces a structural asymmetry between the two SBOM
   shapes.** Capa's `Net` builtin exposes only `get`, not
   `post`; the naive Python POSTs the JSON payload as the
   request body. The Capa transliteration uses a callback-URL
   GET instead - the count of forwarded lines is folded into
   the query string. The wire shape is more disciplined than an
   arbitrary-body POST, and the SBOM still attributes Net
   per-function; the PURL SBOM lists `urllib.request` for the
   whole file and cannot distinguish "this codepath reads from
   the URL" from "this codepath writes a payload to it".

## Functions

| Function | Signature shape | Declared capabilities |
|---|---|---|
| `escape_for_json` | `(String) -> String` | *(none)* |
| `format_as_json` | `(List<String>) -> String` | *(none)* |
| `read_tail` | `(Fs, String, Int) -> Result<List<String>, IoError>` | `Fs` |
| `send_lines` | `(Net, String) -> Result<String, IoError>` | `Net` |
| `forward_log` | `(Fs, Net, String, String, Int) -> Result<Int, IoError>` | `Fs`, `Net` |
| `main` | `(Stdio)` | `Stdio` |

## Naive Python's PURL SBOM proxy

The top-level import block is `import json` and `import
urllib.request`. A PURL-based SBOM generated by syft /
pip-licenses for this file would list `json` (no capability)
and `urllib.request` (capability-bearing stdlib module). It
would say nothing about which functions read the disk vs which
open the network; both are conflated under one signature, and
the `Fs` axis is invisible to the PURL view because the only
import that exercises it (the bare `open` builtin) is not a
named module a PURL SBOM tracks.

The Capa SBOM names both authorities per-function and proves
the pure functions (`escape_for_json`, `format_as_json`) cannot
touch either.
