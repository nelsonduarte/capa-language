# env_loader

A "settings from environment" loader of the `environs` /
`python-decouple` / `pydantic-settings` shape (and of the
hand-rolled equivalents that appear inside Django, Flask, and
FastAPI services).

## What the library does

Reads configuration purely from the process environment: picks
out keys with a given prefix (e.g. `APP_`), strips/lowercases
them into a dict, and validates that a caller-supplied set of
required keys is present. The public API is
`load_settings(prefix: str = 'APP_', required: list[str] |
None = None) -> dict[str, str]`.

## Authority surface

`Env` exercised inside one function; signature declares it.
The prefix-stripping and required-key validation helpers are
pure.

## Why representative

Three reasons:

1. **It is foundational to cloud Python.** The 12-factor
   pattern of reading configuration from environment variables
   is the default deployment story for every cloud-deployed
   Python service. Django, Flask, and FastAPI applications all
   ship some form of this loader, either through dedicated
   libraries (`environs`, `python-decouple`,
   `pydantic-settings`) or hand-rolled inside the app.
2. **The shape conflates env-reading with pure validation.**
   The naive `load_settings(prefix, required)` signature
   covers two logically distinct concerns under one name: a
   step that reads the process environment (capability:
   `Env`) and a step that validates the already-loaded dict
   against a caller-supplied required list (capability: none,
   it is pure dict membership testing). A reviewer reading
   the signature cannot tell either concern apart, nor that
   the second one is unit-testable without any env access.
3. **It is the first `Env`-alone pair in the corpus, and Capa
   structurally narrows the API.** The existing pairs cover
   `Fs + Env + Net` (`config_loader`), `Fs + Env` (`dotenv`),
   and `Fs` alone (`ini_loader`); this pair adds the
   single-axis `Env` case. Beyond per-function attribution,
   the Capa version cannot scan the whole environment at all:
   `Env.get` takes one key at a time, and the capability
   exposes no full-iteration entry point by design - full env
   iteration is a tampering-friendly authority that would let
   any holder of `Env` enumerate secrets it never asked
   about. The Capa caller passes an explicit list of keys of
   interest, and that list is the upper bound on what the
   function can read. This is itself a security narrowing the
   Capa SBOM exposes.

## Functions

| Function | Signature shape | Declared capabilities |
|---|---|---|
| `strip_prefix` | `(String, String) -> String` | *(none)* |
| `load_settings` | `(Env, List<String>, String) -> Map<String, String>` | `Env` |
| `validate_required` | `(Map<String, String>, List<String>) -> Result<Map, String>` | *(none)* |
| `load_validated` | `(Env, List<String>, List<String>, String) -> Result<Map, String>` | `Env` |
| `main` | `(Stdio, Env)` | `Stdio`, `Env` |

## Naive Python's PURL SBOM proxy

The top-level import block is `import os`. A PURL-based SBOM
generated by syft / pip-licenses for this file would list
`os` (a capability-bearing stdlib module). It would say
nothing about which function exercises the environment read,
nor that two of the helpers in the file are pure.

The Capa SBOM names `Env` per-function on `load_settings` and
`load_validated`, attributes `Stdio + Env` to `main`, and
proves the pure functions (`strip_prefix`, `validate_required`)
cannot touch the environment.
