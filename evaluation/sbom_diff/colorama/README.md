# colorama

An ANSI colour wrapper of the PyPI `colorama` shape (~50M
downloads/month; the de-facto choice for coloured terminal
output in Python CLI tools).

## What the library does

Wraps an arbitrary string in an ANSI Select Graphic Rendition
(SGR) escape sequence so that, when emitted to a terminal, it
renders in the requested colour or weight:

1. A small set of foreground colour codes (`RED`, `GREEN`,
   `YELLOW`, `BLUE`, `MAGENTA`, `CYAN`), a bold code (`BOLD`),
   and a reset code (`RESET`), each one a `"\033[Nm"` string.
2. `colored(text, fg)` returns `fg + text + RESET`, or just
   `text` when `fg == ""`.
3. `bold(text)` returns `BOLD + text + RESET`.
4. `strip_ansi(text)` walks the input character by character and
   drops every `ESC ... m` run, returning the unstyled string.

The naive public API is
`colored(text: str, fg: str = "") -> str`,
`bold(text: str) -> str`, and
`strip_ansi(text: str) -> str`.

## Authority surface

*(none)* - pure string transformation; sits alongside slugify/,
tabulate/, textwrap/, humanize/ as a pure-case in the study.
CRITICAL POINT: even though coloured strings are typically
printed (and one would casually call colorama a "terminal output
library"), the colorama functions themselves only produce
strings; the printing is the caller's responsibility. Capa's
per-function attribution makes this distinction crisp.

## Why representative

Three reasons:

1. **It is universally deployed.** PyPI colorama clocks ~50M
   downloads/month; essentially every Python CLI tool that wants
   colour reaches for it (the stdlib has no equivalent, so the
   alternative is to hand-roll the same half-dozen escape
   constants this file ships). The shape of its public API is
   recognisable to any Python programmer who has touched a CLI
   tool.
2. **It surfaces a pure-vs-impure folk-error that PURL cannot
   correct.** A casual reader files colorama under "Stdio"
   because the strings it produces are almost always
   `print()`-ed. The folk-summary is wrong at the per-function
   level: `colored`, `bold`, and `strip_ansi` only construct and
   parse strings, and the Capa version makes that
   machine-checked. A reader who only sees the PURL line
   `pkg:pypi/colorama@0.4.6` has no way to tell whether the
   downstream consumer ever calls `print` on the result or just
   builds it (for tests, structured logs, `--no-color` paths,
   etc.).
3. **It is the PURL-silence case with a twist.** Like
   `textwrap/`, the naive Python imports nothing and the
   colorama PyPI package itself has no cap-bearing runtime
   dependencies, so a PURL SBOM has nothing to say about the
   producer functions at all. Unlike `textwrap/`, the silence
   actively misleads, because the downstream caller does usually
   emit the strings and a reader who confuses producer with
   consumer will misattribute the Stdio call. The Capa version
   names every producer function, declares zero capabilities per
   function, and pins `Stdio` to the one place it actually
   belongs (`main`, the demo caller).

## Naive Python's PURL SBOM proxy

The top-level import block is empty: `naive.py` imports nothing.
The colorama PyPI package itself has no cap-bearing runtime
dependencies (it is essentially the same set of escape-code
constants plus a Windows console shim). A PURL-based SBOM
generated by syft / pip-licenses for this file therefore says
nothing beyond "depends on Python itself", with no per-function
attribution and no signal that the producer functions are pure.

That silence is the comparison failure this pair surfaces. The
casual reader files colorama under "Stdio" because the strings
are almost always `print()`-ed downstream, but a PURL line
`pkg:pypi/colorama@0.4.6` in a transitive dependency tree
conveys nothing about whether the consumer actually emits the
coloured strings or just builds them. The Capa SBOM names zero
capabilities for every producer (`fg_red` ... `strip_ansi`) and
the compiler proves it: a hidden Fs / Env / Net / Stdio call in
any of them would be rejected at type-check time because no
such capability is in scope. Only `main` (the demo caller)
declares `Stdio`, and only because it is the function that
actually prints.

Notes on scope:

- Capa's string escape syntax accepts `\n \r \t \\ \" \' \0` and
  `\u{...}`, but NOT the C-style octal `\033` for the ESC byte
  (the lexer reads `\033` as `\0` followed by the literal chars
  `33`). The Capa version uses `\u{1b}` instead, which produces
  the same byte (0x1B / ESC). The emitted escape sequences are
  byte-identical to what the Python module emits; only the
  source spelling differs.
- The Python module exposes the colour codes as module-level
  `RED = "\033[31m"` constants. Capa's module level holds `fun`
  / `type` items rather than `let` bindings, so the codes in the
  Capa version are zero-arg pure functions (`fg_red()`,
  `reset()`, ...). The call-site cost is one extra pair of
  parentheses; the capability-attribution point is unchanged.
