# rate_limiter

A token-bucket rate limiter of the shape that every Python API
client SDK and standalone rate-limiting library exposes (the
AWS SDK's `tokenbucket`, the Stripe client's retry/throttle
helpers, GitHub's Octokit port, plus the dedicated PyPI libraries
`pyrate-limiter`, `ratelimit`, and `aiolimiter`).

## What the library does

Maintains a token bucket of fixed capacity that refills at a
constant rate, and answers `try_acquire()` calls in O(1):

1. On allocation, seed `tokens = capacity` and record the current
   monotonic time as `last_refill_ts` (Clock).
2. On each `try_acquire`, read the monotonic clock, refill
   `(now - last_refill_ts) * refill_per_sec` tokens (capped at
   `capacity`), and consume one token if at least one is available
   (Clock for the read; pure for the arithmetic and the decision).

Exposes two public functions with the signatures
`make_bucket(capacity: int, refill_per_sec: float) -> dict` and
`try_acquire(bucket: dict) -> bool`.

## Authority surface

`Clock` only, exercised in `make_bucket` and `try_acquire`; the
refill arithmetic and the consume decision are pure.

## Why representative

Three reasons:

1. **It is ubiquitous.** Every Python API client SDK ships some
   form of token-bucket throttling (the AWS SDK, the Stripe
   client, GitHub's Octokit port); the standalone rate-limiting
   libraries on PyPI (`pyrate-limiter`, `ratelimit`,
   `aiolimiter`) each see 100K+ downloads/month and exist solely
   to provide this primitive. A capability-aware SBOM that
   handles this pattern correctly covers a structural component
   of essentially every Python service that talks to a rate-
   limited upstream.
2. **The pure / impure split is surgical.** The refill
   arithmetic (`new_tokens = min(capacity, tokens + elapsed *
   refill_per_sec)`) and the consume decision (`if tokens >= 1`)
   are both pure functions of the bucket state and an explicit
   `now`; the ONLY impure part is the single
   `clock.now_monotonic()` read at the top of `make_bucket` and
   `try_acquire`. Capa exposes this split surgically (two
   functions carry `Clock`, two are pure); Python rolls it all
   into one `time` import and one `dict` return type that says
   nothing about which functions read the clock.
3. **It is the first Clock-only pair in the corpus.** The
   previous Clock-touching pair (`http_retry`) combines Clock
   with Net, so the per-function declared-capability sets there
   are always `{Net}`, `{Clock}`, or `{Net, Clock}` (plus pure).
   This pair isolates Clock without any other authority around
   it, widening the axis coverage of the study and giving the
   harness a clean Clock-only data point for the aggregate
   capability-kind counts.

## Functions

| Function | Signature shape | Declared capabilities |
|---|---|---|
| `fmin` | `(Float, Float) -> Float` | *(none)* |
| `refill_tokens` | `(TokenBucket, Float) -> TokenBucket` | *(none)* |
| `try_consume` | `(TokenBucket) -> AcquireResult` | *(none)* |
| `make_bucket` | `(Clock, Float, Float) -> TokenBucket` | `Clock` |
| `try_acquire` | `(Clock, TokenBucket) -> AcquireResult` | `Clock` |
| `main` | `(Stdio)` | `Stdio` |

## Naive Python's PURL SBOM proxy

The top-level import block is `import time`. A PURL-based SBOM
generated by syft / pip-licenses for this file would list `time`
(a capability-bearing stdlib module that mixes the clock-reading
calls `time.monotonic` and `time.time` with pure helpers like
`time.strftime`). It would say nothing about which functions
exercise the clock and which are pure; the clock reads in
`make_bucket` and `try_acquire` would be conflated with the
purely arithmetic `_refill` under one module-level listing.

The Capa SBOM names `Clock` per-function on `make_bucket` and
`try_acquire` and proves the pure functions (`fmin`,
`refill_tokens`, `try_consume`) cannot read the clock; the
refill arithmetic is pure given an elapsed time.
