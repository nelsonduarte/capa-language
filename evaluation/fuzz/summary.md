## Coverage

The panel covers the eight attack categories called out in the empirical-study plan:

- `cat_capability_aliasing`: Passing the same capability twice in a single call (aliasing).
- `cat_capability_in_data`: Hiding a built-in capability inside a struct field / variant payload / tuple / generic / let / const.
- `cat_env_leak`: Environment-variable exfiltration without Env.
- `cat_fs_traversal`: Filesystem read of sensitive paths from no-Fs functions.
- `cat_llm_dispatch_escape`: LLM-agent-shaped programs trying to escape the §5.4 sandbox by forging or aliasing caps.
- `cat_net_punch`: Outbound network connection without Net.
- `cat_subprocess`: Subprocess spawn (sh, curl, powershell, ...) without Proc.
- `cat_time_channel`: Wall-clock reads (for side-channel exploitation) without Clock.
- `cat_unsafe_smuggle`: Calls to `py_import` / `py_invoke` (the Unsafe-gated escape hatches) without Unsafe.

## Methodology

Each attack program is hand-written to target a specific bypass shape, written to a temp `.capa` file, and passed to `python -m capa --check` as a subprocess. Rejection iff exit code != 0. No probabilistic fuzzing of input mutations; the panel is exhaustive of the categories rather than randomised within them.

**An escape detected here is a paper-relevant finding.** Two such findings were surfaced and fixed during the build-out of this slice: the capability-forge bypass (commit 67d9878) and the user-defined-cap aliasing bypass (commit on the same day). Both were silent soundness regressions in the legacy --python backend that --wasm was incidentally protected against.
