# Runtime benchmark: capa_python vs capa_wasm at macro scale

Generated by `python -m evaluation.runtime.plot` from `results.csv`. Subprocess wall-clock of `python -m capa [--wasm] --run <demo>.capa <args>`. Each cell is the mean of N trials; the range column captures min-max.

|---|---:|---:|---:|---:|---|---|
| audit_trail | 3 | 0.299 | 0.454 | 1.52x | [0.289, 0.307] | [0.446, 0.461] |
| policy_eval | 3 | 0.266 | 0.411 | 1.55x | [0.265, 0.267] | [0.405, 0.423] |
| sbom_watch | 3 | 0.281 | 0.418 | 1.49x | [0.257, 0.299] | [0.415, 0.422] |

**Headline: Capa --wasm pays 1.52x wall-clock overhead vs Capa --python at the macro scale, averaged across 3 downstream demos.** The constant-cost part of the Wasm path (wasmtime spin-up, JsonValue host bridge initialisation, lazy host-import resolution) dominates for sub-second workloads. Steady-state numbers on longer-running workloads are expected to narrow this gap; that measurement is future work.

## Caveats

- **RSS column** in `results.csv` is unreliable on Windows for short-lived processes (psutil samples at 10ms; the Capa subprocesses exit in 250-500ms and the sampler often catches only the initial allocation state). The wall-clock numbers are the load-bearing metric for this slice.
- **Hand-Python and Node baselines** are not in this slice; the headline is strictly an apples-to-apples Capa-backend comparison. Adding those columns is follow-up work.
- **Cold-start dominated**: each trial is a fresh subprocess. Interpreter and wasmtime spin-up cost are counted; this is what a CLI user experiences. A long-running server would see the ratio collapse.
